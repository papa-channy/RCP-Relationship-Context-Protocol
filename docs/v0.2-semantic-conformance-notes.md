# RCP v0.2 Semantic Conformance Notes

**Status:** design notes derived from the first executable v0.2 semantic cases. Non-normative.

Encoding the canonical scenarios as machine-checkable cases exposed several useful model clarifications before any v0.2 wire schema is frozen.

## 1. `DerivationDependency` needs support structure, not only parent links

A flat `derived_from` list is insufficient to decide downstream behavior after one source becomes unavailable.

Example:

```text
Case 1
A ─┐
   ├─> K
B ─┘

A and B are each independently sufficient.
```

versus:

```text
Case 2
A + B together ─> K

Neither source is independently sufficient.
```

Both graphs contain edges from A and B to K, but their invalidation behavior differs.

The semantic model therefore needs to express **independently sufficient evidence paths/groups** or an equivalent concept. The first conformance oracle models this abstractly as `support_sets`:

```json
[["A"], ["B"]]
```

means either source independently supports the assertion, while:

```json
[["A", "B"]]
```

means both are jointly required.

This is a semantic requirement; the final wire representation is still open.

## 2. Re-evaluation is an operation/outcome, not necessarily a lifecycle state

When a source, identity binding, or policy dependency changes, an assertion may need to enter a re-evaluation process. The eventual semantic result can be:

- remain active with new lineage;
- become restricted;
- become disputed;
- become invalidated;
- become superseded;
- be recomputed into a new assertion/version.

The first semantic suite therefore treats `recompute` / `re-evaluate` as **processing outcomes**, not as frozen `ContextLifecycle` states. v0.2 should avoid adding `reevaluation_required` to the public lifecycle registry unless interoperability requires it as externally visible state.

## 3. Projection needs an explicit semantic basis

For multi-party evidence, set inclusion alone is not enough:

```text
source participants = {A,B,C}
target relationship = {A,B}
```

The target being a subset of the source participants is necessary but insufficient. A narrower projection requires an explicit evidence/projection basis.

This suggests that `RelationshipScope` alone may not carry all required semantics. A derived assertion may need a `projection_basis` / derivation relation connecting the source evidence to the narrower target scope.

## 4. Conflict and supersession must remain distinct

Two assertions that conflict are not automatically ordered.

- `conflicts_with` preserves distinct provider/source views until a reconciliation rule resolves them.
- `supersedes` changes currentness because there is an explicit semantic replacement basis.
- later transport receipt alone is neither relation.

The Core therefore needs enough relation semantics to prevent arrival order from becoming hidden state.

## 5. Epistemic transitions need explicit bases for stronger claims

The first oracle fixes only narrow rules:

- `verified_fact` requires an explicit verification basis unless all supporting sources are already verified facts;
- `extracted_fact` requires a direct-extraction basis when derived from a source statement;
- interpretation/inference/strategy remain safe only because they continue to identify themselves as non-verified classes.

This is intentionally smaller than a total ordering over epistemic classes. v0.2 should avoid inventing a universal confidence ladder unless a concrete interoperability case requires it.

## 6. Policy semantics should remain monotonic without defining a new policy language

The semantic suite can test monotonic behavior using abstract normalized dimensions:

- allowed-purpose sets may narrow, not widen;
- external-processing deny survives derivation;
- training deny survives derivation;
- retention maximum may shorten, not lengthen.

This is sufficient to test the RCP-specific inheritance rule while leaving syntax and policy evaluation to ODRL/DPV/AuthZEN/provider-native profiles.

A claimed declassification cannot be represented by a bare boolean. If v0.2 later permits policy loosening, it should require a profile-defined, auditable basis.

## 7. Binding equivalence can be tested before real bindings exist

The first suite wraps the same semantic payload in abstract MCP-like and HTTP-like framing and compares only normalized RCP semantics.

This does not prove a production MCP/HTTP binding. It does prove an important boundary property:

> binding metadata is not allowed to act as hidden relationship semantic state.

The next binding milestone should replace the abstract wrappers with actual minimal MCP and HTTP adapters while reusing the same semantic oracle.

## 8. Provisional concept verdict after first executable pass

| Concept | Result from M4.2 first pass |
| --- | --- |
| `RelationshipScope` | **required** — participant projection cannot be expressed safely without it or equivalent embedded structure |
| `InteractionEvidence` | **required concept, wire form open** — raw evidence may remain opaque but evidence identity/scope must exist |
| `ContextAssertion` | **required / central** |
| `EpistemicClass` | **required** — several safety cases depend on machine-readable distinction |
| `DerivationDependency` | **required and needs strengthening** — must express independent support structure, not only flat provenance links |
| `ContextLifecycle` | **required, but keep processing actions separate from public states** |
| `PolicyReference` | **required at semantic boundary, syntax should remain external/profiled** |
| generic transport/auth/crypto | **not Core** — no semantic case required them |

This verdict is provisional and should be revised when actual MCP/HTTP binding equivalence and cross-implementation tests exist.
