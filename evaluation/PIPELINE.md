# 에이전트 평가 파이프라인 — 초안 (논의용)

## 1. 목표

자체 평가와 독립적으로, 서로 다른 관점의 평가자가 같은 커밋(`68026af`)을 평가하게 한다.
발견 사항은 검증을 거친 것만 종합에 넣는다.

## 2. 핵심 설계 아이디어

**독립성을 규칙이 아니라 구조로 강제한다.** 평가자마다 `68026af`로 분리 worktree를 준다.
그 커밋에는 `evaluation/` 폴더가 없으므로 자체 평가나 다른 보고서를 볼 방법이 아예 없다.

**클린룸 구현자는 허용 파일만 복사한 샌드박스에 둔다.** `docs/IMPLEMENTER_GUIDE_V0_2.md`가 허용한 파일만 복사한다.
오라클 코드가 물리적으로 없으므로 "보지 않았다"를 믿을 필요가 없다.

**이 저장소의 작성자는 ChatGPT다.** 따라서 Claude 에이전트의 클린룸 구현은 "같은 작성자"가 아니다.
사람이 아니므로 L3로 세기는 어렵지만, L2보다 강한 증거다. 표기 방법은 결정이 필요하다.

**보류 케이스(held-out)는 구현자와 다른 에이전트가 명세만 보고 쓴다.** 구현자는 공개 케이스로 개발을 끝낸 뒤에야 보류 케이스를 받는다.
보류 케이스의 기대값은 오라클이 아니라 명세 문장에서 나와야 한다. 오라클과 결과가 다르면 그 자체가 발견이다.

## 3. 단계

```text
0. 준비
   평가자별 worktree(68026af), 클린룸 샌드박스(허용 파일만), 기준·템플릿 배포
        │
1. 독립 평가 (병렬)
   ├─ 명세 감사자        C3 C4 C5
   ├─ 표준 회의론자      C1 C2      "RCP는 필요 없다"를 입증하려 시도
   ├─ 보안 레드팀        C8 C4      불변식 우회 객체 작성
   ├─ 재현성 감사자      C6 C10     문서 주장 대조
   ├─ 보류 케이스 작성자  명세만 보고 케이스와 기대값 작성
   └─ 클린룸 구현자      C9 C7      샌드박스에서 다른 언어로 검증기 구현
        │
2. 충돌 시험
   클린룸 구현 × 공개 케이스, 보류 케이스, 참조 오라클 × 보류 케이스
   불일치는 M4.6 분류(구현 결함, 명세 모호, 스키마·문장 불일치 등)로 분류
        │
3. 검증
   높음 이상 발견마다 별도 검증 에이전트가 재현하거나 반박
   재현 못 한 발견은 종합에서 제외
        │
4. 종합
   기준별 중앙값과 범위, 2점 이상 차이는 불일치 표시, 게이트 판정
   자체 평가와 비교한 결과는 synthesis/ 에 기록
```

## 4. 규모와 비용

| 단계 | 에이전트 수 |
|---|---|
| 독립 평가 | 6 |
| 검증 | 높음 이상 발견 수에 비례, 상한을 두면 3~5 |
| 종합 | 1 |

전체 10개 안팎이다. 클린룸 구현자가 가장 오래 걸린다.

## 5. 결정이 필요한 사항

1. **모델 다양성.** 모든 평가자를 같은 모델로 둘지, 역할별로 모델을 섞을지 정해야 한다.
   같은 모델은 맹점이 겹친다. 대화 이력이 없는 새 ChatGPT 세션을 외부 모델 평가자로 하나 넣을 수도 있다.
2. **클린룸 결과의 증거 등급.** Claude 에이전트의 구현을 L2로 둘지, "L2+ 비관련 모델" 같은 별도 표기를 만들지 정해야 한다.
3. **자체 평가 발견을 평가자에게 알릴지.** 알리지 않는 것을 권한다. 독립 발견률이 자체 평가의 신뢰도를 재는 척도가 된다.
4. **발견 수정 시점.** 평가는 `68026af`로 고정하고 수정은 종합 이후 별도 브랜치에서 하는 것을 권한다.
5. **실행 방식.** 다중 에이전트 워크플로로 한 번에 돌릴지, 역할별로 하나씩 돌리며 중간 결과를 볼지 정해야 한다.
