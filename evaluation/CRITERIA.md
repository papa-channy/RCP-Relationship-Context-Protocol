# 평가 기준 — v1.0 (확정 2026-10-09)

> 변경 이력과 결정 근거는 `DECISIONS.md`에 있다.

## 0. 설계 원칙

RCP는 제품이 아니라 **실험 단계의 프로토콜 연구**다. 그래서 "기능이 많은가"가 아니라
"주장한 의미론이 필요하고, 정확하고, 증명되었고, 안전한가"를 묻는다.

1. **저장소가 스스로 세운 기준을 우선 쓴다.** README는 "RCP는 일반 전송·인가·출처·정책 표준을
   넘어서는 공유 계약이 필요할 때만 정당하다"고 적었다. C1은 이 문장을 그대로 시험한다.
2. **절대 점수와 단계 기대치를 분리한다.** 점수는 "표준 후보로서의 절대 수준"으로 매기고,
   기준마다 v0.2-draft 단계의 기대 점수를 따로 둔다. 차이(점수 − 기대치)가 실제 신호다.
3. **증거 사다리를 구분한다.** 같은 "테스트 통과"라도 자기 검증, 다른 언어 재구현,
   비관련 제3자 구현은 증거 강도가 다르다.
4. **v0.2가 주 평가 대상이다.** v0.1은 보존된 기준선으로 보고 C6, C10에서만 점수에 반영한다.
   v0.1 참조 생태계가 어떤 설계 가설을 검증했는지는 점수 없는 부록 "Legacy Evidence"로만 기록한다.

## 1. 채점 척도

| 점수 | 의미 |
|---|---|
| 0 | 부재. 다루지 않았거나 주장만 있다 |
| 1 | 착수. 존재하지만 핵심 결함이 있다 |
| 2 | 부분. 핵심은 갖췄지만 중요한 빈틈이 있다 |
| 3 | 충족. 사소한 빈틈만 있다 |
| 4 | 모범. 외부 검토를 견딜 수준이고 독립 증거가 있다 |
| N/A | 평가자가 다루지 않은 범위 |

모든 점수에 확신도(상/중/하)와 근거를 붙인다. 심각도는 치명/높음/중간/낮음/참고로 매긴다.

## 3. 기준 상세

### C1. 문제 정당성과 표현 적합성
**핵심 질문:** RCP 고유 개념이 기존 표준 조합으로는 표현할 수 없음을 보였는가?
그리고 대표적인 관계 맥락 상황을 Provider 특화 확장 없이 표현할 수 있는가?

- 고유 개념별로 따진다: 참여자 범위 투영, epistemic class, `support_sets`, 제한 상속, 하류 무효화.
- 각 개념에 "PROV + ODRL + AuthZEN + Shared Signals로는 깨지는 구체 시나리오"가 있는가.
- 반대 가설을 시도한다: 기존 표준의 프로파일 하나로 같은 결과를 낼 수 있는가.
- 표현 적합성: 아래 같은 현실 상황을 현재 모델로 표현할 수 있는지 확인한다.
  여러 관계에 걸친 단언, 시간에 따라 바뀌는 참여자, Provider마다 다른 범위 단위,
  충돌은 아니지만 불확실한 근거, 부분 대체, 당사자별로 다른 의무를 지닌 약속.
  C4는 "정의된 의미론이 올바른가"를, C1은 "필요한 것을 표현할 수 있는가"를 본다.

| 0 | 2 | 4 |
|---|---|---|
| 필요성 주장만 있음 | 일부 개념에 대해 시나리오 근거 있음 | 모든 고유 개념에 반례 시나리오와 기존 표준 매핑 실패가 문서화됨 |

### C2. 표준 경계와 표면 최소성
**핵심 질문:** 위임하기로 한 책임을 실제로 Core에서 뺐는가, 그리고 남은 표면은 최소인가?

- `docs/standards-boundary.md`의 위임 표와 스키마 필드를 대조한다.
- 일반 표준과 겹치는 필드, 채널·제품 특화 값이 Core에 남았는지 찾는다.
- 확장 지점과 미지 확장의 fail-closed 규칙이 명확한가.

### C3. 명세 엄밀성과 내부 일관성
**핵심 질문:** 독립 구현자가 해석 차이 없이 읽을 수 있는가?

- 규범 언어: RFC 2119/8174 키워드 사용 선언과 일관성.
  *관찰:* v0.1 Core는 대문자 MUST를 쓰지만 v0.2 Core와 Wire 초안은 소문자 must만 쓴다.
  README는 v0.2 불변식을 대문자 MUST로 적는다. 평가자는 이 차이가 규범성에 주는 영향을 판단한다.
- `core-v0.2-draft.md` ↔ `wire-v0.2-draft.md` ↔ JSON Schema 사이의 필드, 열거값, 필수 여부 일치.
- 용어 정의 완결성: 모든 핵심 용어가 정의되고 한 가지 뜻으로만 쓰이는가.

### C4. 의미론적 건전성
**핵심 질문:** 불변식들이 서로 충돌하지 않고, 엣지 케이스에서도 결정적인가?

- 불변식 간 충돌 탐색. 예: "독립 근거가 남으면 유지 가능"과 "제한 상속" 동시 적용 시.
- `support_sets` 엣지: 빈 집합, 중복, 상위집합 포함, 순환 의존, 정책으로 일부 경로만 남은 경우.
- Lifecycle 상태 기계가 모든 전이를 정의하는가. 도착 순서 독립성이 실제로 보장되는가.
- 미지·모호 값이 항상 더 제한적인 쪽으로 해석되는가.

| 0 | 2 | 4 |
|---|---|---|
| 불변식이 서술뿐 | 주요 경로는 결정적, 엣지에서 미정의 | 상태 공간 전체가 정의되고 충돌 부재가 논증되거나 형식 검증됨 |

### C5. 적합성 추적성과 오라클 독립성
**핵심 질문:** 모든 규범 요구가 테스트로 이어지고, 테스트가 스펙을 시험하는가?

- 요구 → 케이스 추적표를 만든다. 테스트 없는 요구, 요구 없는 테스트를 센다.
- 양성·음성 케이스 균형. 현재 시맨틱 케이스는 10개 범주 31건, 와이어 스키마 케이스는 20건이다.
- 오라클 독립성: 기대값이 스펙에서 나왔는가, 참조 구현의 출력을 복사했는가.
- 변이 시험: 참조 검증기의 규칙 하나를 끄면 실패하는 케이스가 있는가.

### C6. 재현성과 실행 상태
**핵심 질문:** 깨끗한 체크아웃에서 문서대로 실행하면 전부 통과하는가?

- CI 워크플로 세 개의 모든 단계를 로컬에서 재현한다.
- 의존성 고정 여부, 비결정성, 네트워크 의존, 실행 시간.
- 결과는 `baseline/`에 명령과 출력으로 남긴다.

### C7. 상호운용 증거 강도
**핵심 질문:** 증거 사다리의 어디까지 올라갔는가?

| 단계 | 내용 |
|---|---|
| L0 | 자기 검증. 같은 작성자, 같은 코드 |
| L1 | 같은 작성자, 다른 언어 또는 다른 바인딩 |
| L2 | 같은 작성자, 참조 코드를 보지 않는 클린룸 하네스 |
| L3 | 비관련 제3자 구현이 통과 |
| L4 | 복수 제3자 구현 간 상호 통과 |

MCP↔HTTP 동등성과 Node↔Python은 L1이다. 외부 클린룸 하네스 자체 시험은 작성자 오라클을
재사용하므로 상호운용 증거로 세지 않는다. 하네스 준비 상태는 C5와 C9에서 평가한다.
L3 이상이 없으면 4점은 불가능하다. 제3자 구현이 통과하면 단계 기대치를 3으로 올린다.

### C8. 보안·프라이버시·오용 저항
**핵심 질문:** 위협 모델이 RCP 고유 위험을 다루고, 불변식이 실제로 막는가?

- 고유 위험: 참여자 범위 누출, 테넌트 간 신원 상관, epistemic laundering, 제한 세탁,
  파생 단언을 통한 원본 근거 추론, 철회 후 잔존.
- 오용 시나리오: 감시, 소셜 스코어링, 데이터 브로커 사용을 프로토콜 수준에서 어렵게 하는가.
- `docs/SECURITY_PRIVACY_REVIEW_CHECKLIST.md` 항목별 대응 증거.

### C9. 클린룸 구현 가능성
**핵심 질문:** `spec/`와 구현자 가이드만으로 v0.2 검증기를 만들 수 있는가?

- 평가자는 참조 코드를 보지 않고 최소 검증기를 설계하거나 작성해 본다.
- 막힌 지점을 구현 결함, 명세 모호, 표준 중복, 바인딩 가정, 프로파일 공백,
  보안·프라이버시 우려로 분류한다. 이는 ROADMAP M4.6의 분류와 같다.

### C10. 주장의 정직성과 저장소 일관성
**핵심 질문:** 문서가 말하는 것과 저장소가 증명하는 것이 일치하는가?

- README·ROADMAP의 ✅ 항목마다 대응 증거를 확인한다.
- 과장, 오래된 문장, v0.1과 v0.2 혼동, 깨진 링크.
- 실험 단계 고지와 한계 서술이 충분한가.

## 4. 평가자 역할 배정 (제안)

| 평가자 | 주 기준 | 접근 방식 |
|---|---|---|
| 자체 평가 | 전체 | 작성자 의도와 알려진 약점을 먼저 기록 |
| 명세 감사자 | C3, C4, C5 | 스펙·스키마·케이스 교차 대조, 추적표 작성 |
| 표준 회의론자 | C1, C2 | "RCP는 필요 없다"를 입증하려는 적대적 검토 |
| 보안·프라이버시 레드팀 | C8, C4 | 불변식 우회 시나리오 구성 |
| 클린룸 구현자 | C9, C7 | `spec/`와 `docs/`만 보고 구현 시도 |
| 재현성 감사자 | C6, C10 | CI 재현, 문서 주장 대조 |

## 5. 종합 방법

1. 기준별로 평가자 점수의 중앙값과 범위를 기록한다.
2. 점수 차가 2 이상이면 `불일치`로 표시하고 근거를 나란히 비교한다.
3. 발견 사항은 중복을 합치고 심각도 최댓값을 따른다. 단 근거가 검증된 것만 채택한다.
4. 최종 보고서는 `synthesis/`에 가중 점수, 단계 기대 대비 차이, 게이트 판정, 우선순위 조치를 담는다.

## 6. 부록 지침: Legacy Evidence

v0.1 참조 생태계(5개 Provider, relay, JOSE, Node↔Python, 정책 드리프트 등)는 점수에 넣지 않는다.
각 구성요소가 어떤 설계 가설을 검증했고 그 가설이 v0.2에서 유지·이관·폐기되었는지만 표로 남긴다.
